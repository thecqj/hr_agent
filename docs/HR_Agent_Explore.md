# HR-Agent 方向探索文档

> 本文档指明 HR-Agent 系统的未来构建方向和可尝试的探索，不涉及具体实现细节。

---

## 1. 愿景与定位

HR-Agent 是面向招聘者端的 AI 智能助手，基于 LangGraph 多智能体架构，帮助招聘者完成**简历智能评估、招聘自动筛选、流程自更新**等任务，降低招聘重复劳动，提升筛选效率和决策质量。

**核心价值**：
- 将"收简历 → 看简历 → 打分 → 筛选 → 更新状态"的人工链路自动化
- AI 提供可解释的评估理由，辅助而非替代人工决策
- 通过对话式交互降低操作门槛

---

## 2. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    招聘者（前端）                          │
│              对话界面 + 评估结果展示                        │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP API
┌────────────────────────▼────────────────────────────────┐
│                  HR-Agent 微服务                          │
│                                                          │
│  ┌──────────────┐    ┌───────────────────────────────┐  │
│  │  对话 Agent   │───▶│      任务路由 & 工作流调度      │  │
│  │ (顶层入口)    │    └───────────┬───────────────────┘  │
│  └──────────────┘                │                      │
│                         ┌───────▼───────┐               │
│                         │  招聘工作流     │               │
│                         │ (LangGraph)    │               │
│                         │               │               │
│                         │  ├─ 简历收集   │               │
│                         │  ├─ 简历评估   │               │
│                         │  ├─ 候选人筛选  │               │
│                         │  └─ 状态更新   │               │
│                         └───────────────┘               │
│                                                          │
│  状态持久化：LangGraph Checkpoint → PostgreSQL            │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP API
┌────────────────────────▼────────────────────────────────┐
│                现有 HR 系统后端 (FastAPI)                  │
│         岗位 / 简历 / 申请 / 用户 等业务 API               │
└─────────────────────────────────────────────────────────┘
```

**架构要点**：
- **独立微服务**：HR-Agent 作为独立 Python 服务部署，通过 HTTP API 与现有后端通信，解耦部署和扩缩容
- **两层智能体**：顶层对话 Agent 负责意图理解和任务分发；第二层工作流 Agent 负责具体任务执行
- **不直接操作数据库**：Agent 通过现有业务 API 读写数据，保持业务逻辑一致性
- **LLM 选型后续决定**：模型提供商待定，向量维度将相应调整

**注意：** 当前架构不一定准确，可根据实际情况做调整。

## 3. 分阶段规划

### 第一阶段：智能招聘工作流

**目标**：实现端到端的简历评估 → 候选人筛选 → 状态更新工作流。

**工作流步骤**：

1. **简历收集**：通过现有 API 获取指定岗位下所有待处理（pending）的申请，提取 structured_resume
2. **简历评估**：逐份将结构化简历 + 岗位要求 + 评估规则送入 LLM，输出多维度评分和评估理由
3. **候选人筛选**：根据评估结果和岗位设定的进面人数，由 LLM 筛选进入面试环节的候选人，给出进面/淘汰理由
4. **状态更新**：将评估结果和筛选决策写回系统，更新 Application 状态

**输入**：
- 岗位信息（title、description、skills_required 等）
- 评估规则（公司级模板 + 岗位级覆盖）
- 候选人 structured_resume（直接使用现有 JSONB 数据，零额外解析成本）
- 岗位进面人数

**输出**：
- 每份简历的多维评分（技能匹配、经验相关性、学历达标等）+ 加权总分
- 进面/淘汰决策 + 理由
- 更新后的 Application 状态（ai_score、ai_evaluation、ai_decision 等字段）

**人机协作**：
- 默认人工审核：AI 筛选结果需招聘者确认后才更新系统状态
- 招聘者可选择跳过审核，直接自动执行

**批量处理策略**：
- 逐份评估：每份简历独立调用 LLM，保证评估质量和稳定性
- 需考虑 LLM rate limit 和错误重试机制

**探索方向**：
- 评估维度的定义和权重分配策略（固定权重 vs LLM 动态调整）
- 公司级评估模板的数据结构和存储方案
- 评估结果的可解释性设计（如何让招聘者信任 AI 的评分）
- 评分校准：是否需要少量人工标注样本作为 few-shot 参照

---

### 第二阶段：HR-Agent 对话助手

**目标**：在招聘者端实现对话式交互入口，理解用户意图并调用招聘工作流完成任务。

**对话 Agent 职责**：
- 意图理解：解析用户自然语言指令，识别任务类型
- 参数提取：从对话中提取工作流所需参数（岗位 ID、进面人数等）
- 任务路由：将识别出的任务分发给对应工作流
- 结果反馈：工作流执行完毕后，向用户呈现结果摘要

**交互模式**：
- Phase 2 采用**单轮指令式**对话（如"帮我筛选前端开发岗位的简历"）
- 执行完毕即结束，无上下文记忆
- 对于系统无法处理的任务，明确拒绝并说明当前支持范围

**前端交互**：
- 招聘者端新增对话界面
- 工作流执行通过 HTTP 轮询获取进度：POST 发起任务 → 返回 task_id → 前端轮询 GET /task/{id} 获取进度和结果
- 评估结果以结构化卡片形式呈现（评分、理由、筛选决策）

**探索方向**：
- 意图识别的准确率保障（Prompt Engineering vs 微调分类模型）
- 工作流执行过程中的进度反馈机制设计
- 错误场景的对话处理（岗位无简历、参数缺失等）

---

### 第三阶段：扩展用户体验

**目标**：增强对话体验，支持多轮对话和记忆能力。

**多轮对话**：
- 支持上下文追问（如"上一轮筛选的候选人中，谁的技术能力最强？"）
- 支持指令修正（如"进面人数改成 5 人，重新筛选"）
- 对话中澄清模糊指令（如"你说的是哪个岗位？"）

**记忆系统**：
- 短期记忆：当前会话内的对话上下文
- 长期记忆：跨会话的招聘偏好、历史决策模式等

**探索方向**：
- 记忆的存储和检索策略（向量检索 vs 结构化摘要）
- 记忆的有效期管理和隐私控制
- 多轮对话中的状态管理（LangGraph 的 conversation state 设计）
- 对话历史的压缩与摘要策略（控制 token 消耗）

---

### 后续阶段

根据实际业务和需求扩展：

- **审计 Agent**：追踪 AI 决策过程，确保合规性，检测评估偏见
- **求职者端 Agent**：帮助求职者匹配岗位、优化简历、准备面试
- **招聘分析 Agent**：招聘漏斗分析、渠道效果评估、市场趋势洞察
- **Agent 系统优化**：评估模型迭代、工作流编排优化、成本控制

**探索方向**：
- 多 Agent 协作与冲突解决机制
- AI 决策的公平性和可审计性
- 招聘场景下的合规要求（如反歧视法规）
- 成本优化：缓存策略、模型分级调用、批量推理

## 4. 关键设计决策汇总

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 服务架构 | 独立微服务 | 解耦部署，独立扩缩容 |
| 简历输入 | 直接用 structured_resume | 零解析成本，数据已在系统中 |
| 人机审核 | 默认人工审核，可跳过 | 平衡安全与效率 |
| 评估规则 | 公司模板 + 岗位覆盖 | 兼顾标准化与灵活性 |
| 交互方式 | 对话式 | 降低操作门槛，自然语言指令 |
| 结果存储 | 扩展 Application 表 | 查询方便，减少 JOIN |
| 工作流状态 | LangGraph Checkpoint + PostgreSQL | 持久化可恢复，生态成熟 |
| 评分模型 | 多维评分 + 加权总分 | 可解释性强，支持多维度分析 |
| 批量处理 | 逐份评估 | 保证质量，避免 token 上限问题 |
| Phase 2 对话 | 单轮指令式 | 复杂度后置，先跑通核心链路 |
| 通信方式 | 纯 HTTP 轮询 | 架构简单，工作流耗时可控时体验足够 |
| LLM 选型 | 待定 | 后续决定，向量维度相应调整 |

## 6. 风险与注意事项

- **LLM 输出不确定性**：评分和筛选结果存在随机性，需设计输出结构化约束（JSON Schema / Function Calling）和结果校验
- **Token 成本控制**：逐份评估在简历量大时成本较高，需监控用量并探索缓存/分级策略
- **评估偏见**：AI 可能在学历、性别等方面产生隐性偏见，需审计机制和规则约束
- **数据安全**：简历属于敏感个人信息，Agent 微服务需确保传输加密和访问控制
- **工作流中断恢复**：长工作流可能因网络/服务故障中断，依赖 LangGraph Checkpoint 实现断点续跑
- **API 调用链路延迟**：Agent → 现有后端 API → DB 的链路比直连 DB 更长，需关注性能瓶颈
- **现有幽灵字段**：DB 中 `match_score`、`ai_suggestions` 列与 ORM 模型不一致，需在迁移中统一处理
